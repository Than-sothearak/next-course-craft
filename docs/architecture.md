# Architecture

Coursecraft is one Next.js App Router application. Server routes and server components handle authentication, persistence, authorization, and authoring APIs. Client components provide the interactive authoring experience.

## Boundaries

- `app/`: routes, layouts, and API handlers.
- `components/`: reusable authoring and learner UI.
- `lib/db/`: cached MongoDB connection and Mongoose model registration.
- `lib/auth/`: Auth.js configuration and server session helpers.
- `lib/schemas/`: versioned, runtime-validated content contracts shared by authoring, preview, and export.
- `lib/export/`: shared export runtime logic and learner progress interfaces.
- `lib/dashboard/`: validated folder/course operations, ownership-scoped queries, and dashboard request helpers.
- `lib/<domain>/services/`: server-side operations grouped by the dashboard, editor, and media page/API areas that use them.
- `export/`: standalone static export entry point and build configuration. It must not import Next.js server code, MongoDB, Auth.js, or private storage credentials.
- `models/`: Mongoose models; lessons and assets are independent documents rather than a giant course document.
- `tests/`: Vitest unit tests and Playwright end-to-end tests.

Courses declare `editorType` as `block` or `slide`. The Mongoose default and the reader normalizer treat older records without that field as `block`, so they need no data migration. Block courses continue to store ordered sections on `Course` and lessons with validated blocks in separate `Lesson` documents. Slide courses store versioned, structured canvas documents in the separate `Slide` collection and validate them with `lib/slides/schema.ts`; the slide player renders that schema without using the authoring canvas. Course access checks scope slide reads and writes through the parent course. Block editor APIs and existing block publishers reject slide courses until their slide-specific implementations are available.

Slide schema version 2 adds an optional structured template document. The versioned built-in registry in `lib/slides/template-definitions.ts` defines layout rules independently of the validated text, image, list, and navigation-button slots in `template-schema.ts`. Replacing a template copies compatible slots and retains unused slots for a later compatible design; resetting design never resets content. Templates use responsive layout, while existing version 1 canvas slides keep their scaled coordinates.

The latest clarification defines **fixed canvas → prebuilt interactive objects → independent timeline layers**, keeping `editorType: "slide"` and the existing routes. Version 3 compositions validate free object placement, appearance, timing, media, interaction and assessment content through `lib/slides/blocks.ts`. Accordion, tabs, flashcards, quizzes, text, images, audio/video, SVG shapes and navigation buttons are independently positioned objects. `object-canvas.ts` materializes coordinates before edits/reordering, so hiding or changing a layer's timing never reflows another object. Explicit legacy `layout: "flow"` documents retain their older flow renderer unless an enabled master supplies a fixed canvas.

The canonical design grid is 1280×720. HD renders it directly; Full HD scales the complete composition to 1920×1080. Object bounds, rotation and stacking are independent of timing. The fixed scene clips its outer bounds; a complex object's content scrolls inside its own box. Normal authoring uses selection overlays; learner/timing preview runs the actual interactions. Fully transparent objects do not intercept pointer input.

Add page creates a blank fixed canvas. Add object opens the prebuilt object gallery. `object-layouts.ts` inserts independently editable text/image/card/button placeholders from the twelve content layouts. Existing template content, including retained slots, stays editable without flattening when combined with new objects. The object inspector provides coordinates, dimensions, rotation, typography, color, opacity and shape/button settings. Existing canvas documents retain their original editor. Geometry and nested media use the same revisioned saves and duplication services.

`object-canvas-surface.tsx` and `learning-page-surface.tsx` are the shared browser-only scene boundary. The authoring viewport and learner player scale the same fixed scene; thumbnails account for the selected HD/Full HD resolution. The existing Rise learner/editor continues to use its responsive block renderer.

Slide Masters follow `docs/slide-master-plan.md`. A versioned, Zod-validated optional master lives in `Course.slideTheme`, separate from foreground objects, and saves through the existing owner-scoped `slideThemeRevision` boundary. Sparse `composition.masterOverrides` deep-merge only modified fields, so other settings keep inheriting course edits. Legacy canvas/template slides use equivalent top-level `masterOverrides` and `numbering` metadata to keep their content version unchanged. `composition.numbering` supports a manual label or hiding; automatic values derive from current slide order plus the shared starting value.

Institutional Green uses editable React/CSS/SVG header, angled banner, logo placeholder/owned image, pale geometric background, rounded content region, green footer and numbered circle. `master-surface.tsx` is shared by editor, learner and thumbnails. Master decorations ignore pointer input and remain visible independently of timeline object filtering. Foreground boxes map their unchanged saved design coordinates into the master safe area, with separate inverse pointer scales for X/Y; their contents reflow/scroll in those boxes. Applying or disabling a master never rewrites object geometry, assets or source trims. Legacy templates/canvases fit inside the same protected region.

The master editor uses a local draft with live preview, apply/cancel, reset and undo/redo. Applying a course master enters the theme draft store; applying a slide override enters the slide draft store. Reset to master clears only the slide master/number overrides. Logos and backgrounds use the existing authenticated media picker, and the server rejects non-image, unready or foreign course assets. Course duplication remaps master and override image references into independently owned copies. Saved-master libraries, advanced animations and master-aware static slide publishing remain later phases.

The expandable timeline supports icon playback controls, ruler scrubbing, duration, millisecond timing, per-layer start/end fields, whole-clip pointer/keyboard movement, edge trim handles, adaptive ruler ticks, zoom/fit and horizontal/vertical scrolling. Snap targets include the playhead, other clip edges and slide boundaries; Alt bypasses snapping. Drag preview is transient and shared with the canvas/inspector; a completed gesture enters autosave/history once, while cancellation leaves the document unchanged. Memoized rows use a shared CSS playhead during coordinated browser-time playback. A draggable separator resizes the timeline while reserving preview space. Validated browser preferences retain panel height, zoom, snapping, light/dark appearance and track-name width separately from saved page content. Global monitor volume/mute and per-track mute/solo control editor audio/video output without changing authored volume or learner playback; deleted solo tracks are reconciled. See `docs/slide-timeline-plan.md` for the accepted immediate scope. Start fields move a clip's schedule; edge handles trim it. Audio/video edge trimming updates source in/out metadata without rewriting the original asset. Browser-loaded source duration bounds trims and initializes the track length. Replacing media clears stale duration/trim metadata. Audio/video can be added directly from the timeline through the existing course media picker. Volume, loop, transcripts and synchronized playback remain available. The existing course-owned S3 upload lifecycle accepts supported audio MIME types with a 100 MB limit; images and video retain their prior limits. Referenced owned assets must be ready and match the new media block kind. No waveform extraction, media transcoding or caption generation runs on the server.

The content-page player shares browser-only block rendering and the existing quiz grading engine. Ordinary reading pages use explicit page completion; required activities must be explored, quizzes passed and configured media completed before marking a page complete. A learner content menu shows actual completion independently of page position. Preview completion persists in browser storage scoped by authenticated actor/course and invalidates entries after page revisions. This is preview progress, not server-side learning records or LMS reporting; slide HTML/SCORM export remains pending.

Slide themes live in a separate optional `Course.slideTheme` subdocument with `slideThemeRevision`, leaving the block theme contract intact. Six built-in presets and per-slide design overrides resolve into CSS variables with readable text and button colors. `components/slides/slide-surface.tsx` is the browser-only presentation boundary shared by editor, gallery thumbnails, and learner preview. Template layouts use container queries to stack columns, wrap text, and retain touch-friendly controls. These components import no Next.js runtime, authentication, or database code and are ready for the later slide export strategy; they are not yet connected to HTML/SCORM packaging.

`lib/slides/draft-store.ts` serializes revisioned autosaves, reconciles server revisions with edits made during requests, and keeps local changes after conflicts or network errors. Content undo/redo uses the latest server revision. The editor stores mode, selection, viewport, and state-preview choices only in client state. Corrected validation errors resume autosave; conflicts and network errors require explicit recovery. Structural slide actions flush pending edits before changing the slide list. Slide saves check ready course-owned asset references, including retained template slots. Slide/course duplication preserves template data, remaps nested media, and copies the course slide theme independently.

The standalone export runtime is bundled separately by Vite as a build tool inside this repository. Its build output consists only of static HTML, CSS, and JavaScript. The authenticated HTML publishing route embeds that bundle, the validated course snapshot, and owner-scoped course media in one downloadable HTML file. The SCORM 1.2 publishing route packages the same compiled export runtime with a validated snapshot, owner-scoped media, the root-level `imsmanifest.xml`, and the referenced schema files. SCORM 2004 uses the same runtime and packaged media with its own manifest and `API_1484_11` adapter. The PDF handout route validates the same course snapshot, includes owner-scoped PNG and JPEG images, and renders lesson and activity text with bundled Latin and Khmer fonts. Quiz handouts show prompts and choices without answer keys or feedback. The browser-only export saves resume and completion state through either LMS API when available; without an LMS it falls back to browser storage.

The browser-only learner view lives in `app/courses/[courseId]/preview/course-preview.tsx` and is shared by the authenticated preview route and the standalone Vite entry point. App-only navigation and publishing actions are supplied by the preview route wrapper, so the static export does not depend on Next.js APIs. The SCORM adapter lives in `export/src/scorm-runtime.ts` and depends only on browser APIs and the shared learner progress contract. Quiz best scores and passed-quiz IDs are saved with resume state; the adapter reports raw scores as attempts are graded and reports assessment success with course completion. Both outputs use `app/globals.css` for matching layout, typography, and animations.

Phase 11 learner navigation adds search across lesson and quiz titles, collapsible section groups, per-section completion summaries, and a saved course-level progression mode. Authors can allow free navigation, require completion of each lesson in sequence, or require completion of activities and Continue gates before unlocking the next lesson. These rules run in the shared learner view, so the authenticated preview and standalone export use the same locks and resume state.

Free navigation marks content lessons complete after the learner reads all revealed sections to the end; interactions are optional except where a Continue button requires completion above. Those Continue gates require both reading and the interactions above in every navigation mode. Next section stays hidden while any Continue gate remains unrevealed or incomplete, including gates with completion set to None. Completion does not fabricate interaction records. Sequential/restricted courses keep their lesson interaction requirements, and graded quiz lessons still require a passing attempt in every mode. The same completion snapshot drives preview checkmarks, saved resume state, and SCORM completion reporting.

Course themes are validated in `lib/editor/theme.ts`, persisted in the course document, and included in the revision-checked editor snapshot. The course editor exposes palette presets, custom brand and accent colors, and local system font choices. The shared learner view maps these values to CSS custom properties, so the authenticated preview, HTML package, and both SCORM formats render the same branding without loading external fonts or assets.

Theme settings also configure the course introduction cover: Gradient, Solid color, Image, Waves, Geometric, or Editorial. A shared cover surface renders template thumbnails, the live settings preview, and the learner overview with container-based typography. Authors can set cover/text colors and alignment; image covers use the existing course media library, with image descriptions, cropping position, and overlay opacity. The optional `theme.cover` subdocument preserves older themes without a migration. Saves verify ready image ownership within the current course. Existing recursive HTML/SCORM media packaging includes cover assets and rewrites their URLs for offline use; the shared cover schema accepts those rewritten image sources while the save service requires an owned media-library URL.

Code examples use the existing richText block with escaped source inside pre/code elements. Seven presets combine six themes with optional titles and explanation paragraphs above or below the code. The shared TipTap code extension preserves theme/language attributes and applies syntax colors as view decorations, keeping stored source text intact. Lesson rich text and learner previews accept multiple document elements so titles, paragraphs, and code survive editing and export; title and statement editors retain their single-element behavior. AI code seeds can include nullable codeExample metadata that selects the same presets and supplies the explanation; old seeds without it remain supported.

## Persistence and security

Process-step blocks support Classic cards, Numbered, Timeline, Spotlight, and Minimal layouts, with optional accent colors and numbered badges. Existing blocks keep the Classic layout. Content settings and prebuilt template changes preserve authored step IDs and instructions; editing or adding steps retains the selected presentation settings. The shared process renderer and its navigation/card components are used by the editor, preview, and static HTML/SCORM learner export, with the same interaction tracking in every layout.

Process-step layouts use their container width for timeline columns, card padding, progress, and navigation controls. Narrow previews stack timeline navigation above the card and allow the step list to scroll horizontally. Previous/Next controls stack below 320px; long instructions wrap within the card. Navigation labels display two lines while the accessible button name and active card retain the complete title.

The author preview navbar Edit action routes to the active lesson and, when applicable, its visible content block using the lesson editor's `blockId` query parameter. The lesson route accepts a block target only when it belongs to the loaded owner-scoped lesson; the editor scrolls to that block and focuses its inline text or opens its content settings. Standalone learner exports omit author controls.

The shared preview measures the space below its toolbar and fits mobile/tablet frames to both available dimensions. The actual screen width controls the compact lesson menu. Only the selected lesson participates in layout; inactive lessons stay mounted to preserve interactions and reading positions. Each lesson has one bounded vertical scroller, and progress is recalculated when its height changes.

Next/Previous section buttons use a short directional slide within the bounded lesson reader. The outgoing lesson briefly becomes an inert absolute overlay, so navigation never adds stacked lesson heights or scrolls an outer container. The transition cancels on another navigation, reader resize, device/orientation change, or leaving Learn mode; completion restores the inactive lesson's hidden state. Reduced-motion preferences and browsers without the animation API use an immediate switch.

Flip-card grids, typography, and padding respond to their own container width, including simulated mobile frames inside a desktop browser. Narrow blocks stack cards in one column; larger blocks allow two columns, or three for a three-card set when space permits. Both faces size to their content, wrap long labels, and constrain images without changing flip interactions or completion tracking.

MongoDB is accessed only from server-side code. Every data access path must scope reads and writes to the authenticated owner or workspace. Zod validates untrusted input before persistence. Mongoose schemas add database-level validation, indexes, and timestamps. Secrets stay in server environment variables.

The Phase 2 dashboard uses `/api/folders`, `/api/courses`, and `/api/dashboard`. Folder deletion is blocked while it contains courses or subfolders. Course deletion requires an exact title confirmation and marks the document as recently deleted, preserving its content references. The dashboard filters deleted documents from normal listings.

The dashboard supports Cache Components and Partial Prefetching with a static navbar and matching skeletons for the account menu, folder sidebar, folder cards, and course cards. URL parameters resolve behind Suspense; the authenticated profile, folder navigation, and workspace listing stream through separate boundaries. Navigation and listing queries run concurrently with request-scoped session deduplication. Shared client state connects sidebar actions to workspace dialogs and refreshes folder counts after mutations. Initial server data is reused without an immediate duplicate API request; filter changes show the same card skeletons and cancel superseded requests.

Course duplication copies validated sections and lessons, the ready media library, and referenced source media into independent private S3 objects and destination-scoped asset records. Authors can copy a personal course into a shared workspace or copy between workspaces; copies into a different workspace start at the root. It remaps nested media URLs, rich text, quiz images, dashboard covers, and theme covers. Course-local content identifiers and quiz answer relationships remain intact; database IDs and asset URLs are new. The new course is created only after its media and lessons are ready. Source revision checks reject inconsistent reads, and failure cleanup removes only the attempted copy's records and files, with best-effort logging if cleanup itself fails.

Phase 13 collaboration uses shared workspaces that own their courses, folders, and media. The workspace owner retains content ownership; memberships grant owner/admin/editor/viewer access, and every dashboard, editor, media, generation, and publishing operation checks the member's role before using that owner scope. Personal data remains in the personal scope. Courses record their creating account separately from the workspace owner so the author byline remains correct for teammates; older courses fall back to their owner. Invitation tokens are random, stored only as SHA-256 hashes, expire after seven days, and can only be accepted by a signed-in account whose email matches the invitation. Workspace folder uniqueness is scoped by owner, workspace, parent, and normalized name. Run `MONGODB_URI=... npm run migrate:workspace-folder-index` once against an existing database before deploying workspace folders; the migration creates the new unique index and removes the two previous folder uniqueness indexes.

The Phase 3 course page is served at `/courses/[courseId]/edit`, with lessons edited individually at `/courses/[courseId]/edit/lessons/[lessonId]`. Adding a lesson uses `/api/courses/[courseId]/lessons`; editor saves persist through `/api/courses/[courseId]/editor`. It stores ordered section metadata on the course and stores lessons as separate documents with stable editor IDs. Autosaves validate the complete snapshot and check the course revision. Replica sets use a MongoDB transaction; standalone MongoDB uses an atomic course revision lock and restores the prior course and lesson snapshot if a write fails. A stale revision returns a conflict so the editor can preserve the author's local changes and ask them to reload.

Duplicating content keeps the current editor route and saves the new lesson in its source section. Copies receive independent block/question/choice data and IDs, with quiz answer keys mapped to the copied choices. The content actions menu can move a lesson or quiz to another section of the same course, appending it there and normalizing source/destination ordering. Both actions use the editor's existing history and revision-checked save path.

Phase 4 media uploads use short-lived S3 presigned POST policies. The application stores the private object key and ownership metadata in `Asset`, and lesson blocks reference an authenticated `/api/assets/[assetId]/file` route rather than a bucket URL. Configure S3 bucket CORS to allow `POST`, `GET`, and `HEAD` from the development and production app origins; keep S3 Block Public Access enabled. The application IAM identity needs `s3:PutObject`, `s3:GetObject`, and `s3:DeleteObject` on the configured bucket prefix.

AI course generation is an authenticated, app-only Node.js route. Prompt-only input produces a structured draft that is validated against generation constraints and the shared block schema before it reaches the editor. PDF/PPTX source generation runs as an owner-scoped, resumable MongoDB job: the server indexes the document, extracts bounded page batches, plans lesson ranges, generates Pre/Learn/Post stages independently, validates source coverage, and checkpoints each completed unit. Uploaded source bytes are held temporarily in the job document while bounded extraction is running, then cleared when the inventory is complete. Job and checkpoint records expire after 24 hours. Authors review the generated outline and apply it through the existing revision-checked editor save path. Generated illustrations are stored as owner-scoped private S3 assets and inserted through their authenticated asset routes; they are supplemental and do not count as preserved original visuals.

Each structured generation stage shares a two-request allowance and one deadline across transport retries, JSON repairs, and application-validation corrections. Temporary rate limits, selected server errors, and temporary connection failures may retry after a short jittered delay, honoring Retry-After; delays above 30 seconds or beyond the stage deadline stop instead of retrying early. Billing, authentication, request-configuration, output-limit, and timeout failures do not automatically resubmit generation. Provider schemas enforce quiz option bounds, exact activity counts, and text limits before application validation. Prompt-only drafts also repair incorrect lesson counts or missing template activities within the same allowance; source stages retain their existing checkpoints for manual resume.

Learn generation uses a compact response schema with only the fields relevant to each block type. The server restores neutral unused settings and validates the same editor seeds; existing checkpoints remain readable. Learn writing uses low reasoning effort with the selected model and the existing two-minute request budget. If a source group times out or reaches its output limit, the job checkpoints smaller parts for subsequent requests, splitting between complete pages or source elements without cutting code listings. Completed parts are saved independently and merged in source order into the originally planned lesson; page grouping, titles, and source references remain intact. The progress response reports saved parts while retaining the two parent steps. Older timed-out jobs prepare smaller parts when resumed, using their saved source inventory and plan. A coverage-repair timeout retains an earlier validated draft with an explicit coverage warning rather than discarding it.

The generation dialog always shows two parent steps while generating. Prompt-only requests show Prepare prompt as complete and Generate course as active with indeterminate progress until the single request finishes. File requests show initial source steps immediately, then use the job's reported progress. Each run clears stale progress, and the loading panel can scroll on short screens without clipping the steps. Displaying progress does not send extra generation requests.

The prompt field starts with editable instructions to follow the selected structure and settings. Optional instruction buttons append source-preservation, code-explanation, guided-practice, summary/next-lesson, or Continue-button guidance without replacing authored text or submitting a request. The controls prevent duplicate additions and respect the existing 5,000-character limit; prompts do not hardcode a language or grouping mode.

Authors can cancel an active generation or a saved source job from the dialog. Cancellation aborts browser requests, stops subsequent source stages, and clears the matching saved reference; a provider request already sent may still finish. Late responses cannot replace a newer run. Source cancellation is owner/course scoped, preserves an already completed draft, and removes checkpoints even when an in-flight stage writes after cancellation. Missing or expired saved jobs clear with a retry message and retain the prompt/settings; starting fresh requires an explicit Generate draft action.

## Authentication

Auth.js v5 uses the existing MongoDB adapter with a validated profile wrapper that creates server-generated user IDs and explicitly persists `viewer`/`pending` for new registrations. Native OAuth writes bypass Mongoose defaults, so authorization fields are protected in the wrapper. Sign-in records last-login time and a credential-free audit event. Reauthentication never resets approval or permissions. Google requires a verified email; linking a new Google identity to an Admin/Super Admin additionally requires an already authenticated session for the same active account. Active users can explicitly connect providers from `/account-status`.

Platform authorization lives in `lib/auth/policy.ts` and `lib/auth/authorization.ts`. Current MongoDB account status and role policies authorize each privileged request; OAuth session/JWT claims only identify the actor. Missing/invalid authorization data fails closed. Statuses are pending, active, rejected and suspended; platform roles are Super Admin, Admin, Editor and Viewer. Mutable role policies and optional per-user allowlists can only narrow immutable role ceilings. Approval is independent of authentication. Pending/rejected/suspended users retain their account-status and sign-out paths.

Existing owner/workspace checks in `lib/workspaces/access.ts` now intersect platform permissions with ownership, workspace membership, and explicit `CourseAssignment` roles. Administrators need `courses.manage_all` plus the requested operation; author roles never grant access to another private course by themselves. Media, editor, generation, publishing and exports share these checks. Publishing requires both publish and export permissions. Media files stream through the authenticated route instead of exposing reusable private download URLs; static learner exports stay independent of authentication APIs.

`lib/admin/` provides scoped queries and transactional mutations for `/admin` and its APIs. A singleton security control serializes mutations and bootstrap so simultaneous changes cannot remove the last active Super Admin. Sensitive changes and their safe audit metadata commit together. Ownership transfer updates course/asset/job scopes, preserves creator/content IDs, moves the course into the target's personal root, and rejects active saves, generation leases/jobs or upload policies. Maintenance scripts explicitly migrate legacy accounts to pending when status is absent and bootstrap one existing account by protected ID and operator confirmation. Administration requires authenticated transactional MongoDB; see `docs/admin-operations.md` for rollout, migration, bootstrap and test instructions.

## Runtime and deployment

Mongo-backed route handlers use the Node.js runtime. The export bundle is built with `npm run build:export` into `public/course-export`; this is static output that publishing routes package as HTML or SCORM. Export work belongs in isolated server-side service modules and must respect hosting request and memory limits.
